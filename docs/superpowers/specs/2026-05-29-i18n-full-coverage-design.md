# HbwebExpo 全页面与提示文本国际化设计说明

## 目标

在保留现有 `i18next + react-i18next` 架构的前提下，完成 `HbwebExpoApp` 所有页面与提示文本的国际化，使中英文切换后，页面可见文本、交互提示、错误提示、弹窗与状态展示都能跟随语言稳定输出。

## 当前现状

- 项目已存在国际化基础设施：`/Users/sean/DEV/HbwebExpo/HbwebExpoApp/src/shared/i18n/i18n.ts`
- 当前已接入 `zh/en` 两套 locale 资源，并按 `common + screens/*` namespace 组织。
- 多数页面主文案已经通过 `t(...)` 接入，但仍存在以下漏点：
  - 部分页面或模块存在硬编码中文/英文文本。
  - 多处 `Snackbar`、`Alert.alert`、失败兜底直接使用 `error.message`。
  - 少量 placeholder、辅助提示、状态描述仍未完全收口。
  - 后端返回的中文错误、状态描述、角色名在英文界面下可能直接暴露。

## 范围

本次纳入国际化范围：

- `app/(auth)`、`app/(tabs)`、`app/staff/[userGuid].tsx`
- 被页面直接使用的 `src/components/**`
- 承载页面 UI 的 `src/modules/**`
- 所有用户可见文案，包括：
  - 页面标题、副标题、导航文案
  - 按钮、菜单、分段选择器、表单 label
  - placeholder、helper text、空状态、加载态
  - Snackbar、Alert、成功/失败提示
  - 状态文案、筛选项文案、动态插值提示

本次不作为主目标处理，但需要避免误伤：

- 商品名、门店名、员工名、供应商名等业务数据本身
- 接口字段名、日志文本、测试样例数据
- 后端协议要求的原始中文枚举值

## 发现的主要问题

基于当前源码扫描，风险主要集中在两类：

### 1. 交互提示兜底未国际化

多个页面在失败场景直接展示 `error.message`，例如：

- `app/(tabs)/warehouse.tsx`
- `app/(tabs)/local-supplier-invoices.tsx`
- `app/(tabs)/home.tsx`
- `app/(tabs)/domestic-purchase.tsx`
- `app/(tabs)/cart.tsx`
- `app/(tabs)/installment-orders.tsx`
- `app/(tabs)/settings.tsx`
- `app/(tabs)/product-query.tsx`
- `app/(tabs)/store-vouchers.tsx`
- `app/staff/[userGuid].tsx`

这会导致英文界面中直接出现后端中文错误，或者出现未统一风格的英文原始报错。

### 2. 局部硬编码与格式化逻辑分散

当前已发现的代表性位置包括：

- `app/(auth)/login.tsx` 中仍有少量界面切换标记与错误判断分散处理
- `app/(tabs)/domestic-purchase.tsx` 中存在导出/拼接文本
- `src/modules/local-supplier-invoices/date-range.ts` 中默认日期区间文案写死
- `src/modules/device/api.ts`、`src/modules/auth/login-errors.ts`、`src/shared/api/auth-error.ts` 中存在面向展示的状态或错误关键词判断

这些位置需要收敛到统一的展示层国际化策略。

## 方案对比

### 方案 A：只补页面硬编码文本

优点：

- 改动快
- 风险低

缺点：

- 英文界面仍会暴露后端中文错误
- 体验层面仍不算“完成国际化”

### 方案 B：页面补漏 + 提示/错误映射收敛

优点：

- 能覆盖真实用户最常遇到的国际化缺口
- 不需要重做底层架构
- 与当前代码组织兼容度高

缺点：

- 需要补一层错误消息与状态展示策略

### 方案 C：方案 B + 自动化扫描与校验

优点：

- 除了补齐当前缺口，还能防止未来回归
- 对双语资源一致性更稳

缺点：

- 本轮工程化收尾工作会更多

## 推荐方案

采用 **方案 B 为主，顺手加入轻量的资源一致性校验**。

也就是：

- 保留现有国际化架构
- 全量补齐页面与提示文案
- 建立统一的错误/状态展示映射
- 增加一个轻量检查，保证 `zh/en` key 不漂移

## 设计细节

### 1. 资源组织保持现状，继续按 namespace 收口

- `common.json`：放通用动作、通用状态、通用错误、打印/扫码/加载等共享文案
- `screens/*.json`：继续放页面私有文案
- 若某类错误或状态跨多个页面复用，优先沉入 `common`

不引入新的大规模资源结构重组，避免这轮国际化变成重构工程。

### 2. 页面可见文案全部走 `t(...)`

本次会逐页检查并补齐：

- 标题、副标题
- 按钮与菜单
- placeholder
- helper text
- 空状态
- Modal / Alert / Snackbar 文案
- accessibilityLabel

对已经使用 `t(...)` 的页面，只补漏点，不做无关改写。

### 3. 新增统一的“用户可见错误消息解析”层

需要引入一个共享策略，用来替代页面里散落的：

- `error instanceof Error ? error.message : t(...)`
- ``${fallback}: ${error.message}``

默认规则定为：

- 中文界面：允许保留较多后端原始中文消息
- 英文界面：优先映射为本地化英文提示
- 若无法识别错误类型，则回退到页面定义的英文通用失败文案
- 仅在确有必要时拼接原始错误细节，避免把后端中文原样暴露给英文用户

这一层优先处理：

- 登录错误
- 认证/授权错误
- 打印失败
- 网络失败
- 查询/保存/刷新失败
- 设备绑定、仓库位置绑定、商品查询等高频业务失败

### 4. 状态、角色、权限、后端描述做展示映射

以下内容如果会直接显示给用户，需要建立展示映射：

- 设备状态描述
- 登录状态说明
- 角色/权限展示标签
- 业务状态码对应标签

原则：

- 后端值保持原样参与业务逻辑
- UI 展示通过映射后的本地化文案输出
- 业务数据名称本身不强制翻译

### 5. 日期、数字、金额展示跟随语言

已有 `resolveLocaleTag(language)` 基础，后续应统一检查以下场景是否走本地化格式：

- 日期区间文案
- 数量和金额展示
- 统计概览中的数值文本

本次优先修补已经发现的默认日期区间与动态提示文案。

### 6. 轻量校验

新增一个轻量检查，至少保证：

- `src/locales/zh/**` 与 `src/locales/en/**` 资源 key 对齐
- 本次新增文案不会只加中文或只加英文

如果实现成本合适，可以补一个“用户可见源码硬编码扫描”脚本或执行清单，但不把它做成过重基础设施。

## 实施顺序

### 阶段一：盘点与公共策略

- 收敛共享错误消息解析函数
- 梳理共用状态映射与通用文案归属
- 补资源缺失 key

### 阶段二：高频页面补齐

优先处理存在 `Snackbar` / `Alert` / `error.message` 直出的核心页面：

- 登录
- 首页
- 商品查询
- 仓库
- 购物车
- 设置
- 员工资料

### 阶段三：列表与业务页面补齐

- 订单
- 分期订单
- 门店代金券
- 本地供应商发票
- 澳洲进货单
- 广告
- 季节卡
- 用户管理
- 考勤相关页面

### 阶段四：校验与验收

- 检查 locale key 对齐
- 切换 `zh/en` 人工巡检主要页面
- 再扫描用户可见源码中的残留硬编码

## 验收标准

满足以下条件才算完成：

- 中英文语言切换后，所有页面核心可见文案都能跟随变化
- 所有主要提示文本，包括 Snackbar、Alert、空状态、placeholder、helper text 已接入国际化
- 英文界面不会大面积暴露后端中文错误或中文状态描述
- `zh/en` locale key 保持一致
- 扫描结果中，用户可见层残留硬编码仅限明确允许的业务数据或格式样例

## 当前默认决策

若用户未额外指定，本次实施采用以下默认决策：

- 英文界面下，后端返回的中文错误和状态描述：**优先映射成本地化英文；映射不了则回退到英文通用失败文案，不直接原样透出**
- 中文界面下，可保留后端中文错误作为更贴近业务现场的反馈
- 不额外引入第三套语言，也不更换国际化框架

## 需要用户确认的唯一问题

英文界面下，未知后端中文错误是否允许附带原始错误细节。

推荐默认值：

- 不附带原始中文细节，直接显示英文通用失败提示

这样能保证英文界面一致性最高，也最符合“所有页面和提示文本完成国际化”的目标。
